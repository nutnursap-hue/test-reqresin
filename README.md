# Блок 1. Работа с докой груминга

После прочтения всей документации, по крайней мере для меня, сразу стало неясно несколько вещей.
Лучше пройдусь тут по фактам и по определённым пунктам.

## 1. Недочёты, противоречия по первому блоку

### Противоречие про «один клик»

Что значит «в один клик»? Пользователю как минимум понадобится пройти через редиректы на другой
платёжный сервис, самому произвести оплату, потом ещё в Roblox принять трейд, и для этого бота
ещё надо добавить в друзья.

Я понимаю, что также во флоу написано, что пользователь может иметь на балансе шекели и допустим
есть уже добавленный в друзья в Roblox бот, но это не означает, что всё это будет происходить в
один клик — этот же предмет всё равно нужно принять через трейд. Для этого юзеру нужно будет зайти
на сервер, а это снова не одно действие. Лучше всего уточнить этот момент (больше докапываюсь к
самой формулировке «в один клик»).

По факту это два разных юзер-кейса, которые нужно будет описывать и прописывать под них аналитику,
разделяя их на отдельные задачи в разработке.

### Неправильно разделён статус Success (не особо он прописан)

В этом пункте у меня вопрос на счёт того, когда именно ставится статус Success? Просто написано,
что платёжка возвращает успешный вебхук и потом система шлёт событие в RabbitMQ, только тут не
сказано, с каким статусом приходит сам вебхук (по моему пониманию, если написано «успешный
вебхук», наверное статус — Success). Передача самого предмета через Computer Vision также важна, и
только после данной фиксации по факту должен присваиваться статус Success.

Также никак не описаны промежуточные статусы — понимаю, что у нас в любом случае grayBox, но это
не означает, что нам не нужно описание всех статусов.

### Ограничения в Roblox

Почитал в интернете — оказывается, в Roblox есть ограничение на количество друзей в френдлисте, и
по факту бот может быть переполнен: как только у бота не останется места для друзей, он не сможет
принимать новые заявки в друзья или отправлять их (если так вообще будет реализовано). В таком
случае у пользователя не будет возможности получить свой предмет, и нужно реализовать функционал
по контролю количества друзей у бота и удалению старых, либо перенаправлению на других ботов, а в
самом плохом сценарии — отмену заказа и возврат средств.

### Неправильная работа Computer Vision

Этот момент вообще никак не описан. По информации из открытых источников, Computer Vision хоть и
редко, но иногда ошибается и может не распознать передачу предмета. Будет ли вообще обсуждаться
момент, когда Computer Vision не зафиксирует уже произведённую передачу — что в этом случае нужно
будет делать пользователю, будут ли скриншоты или видеозаписи как доказательство?

### Способы оплаты не разделены

Есть два флоу оплаты — через внешний платёжный сервис и с баланса пользователя. Не особо понятно,
будут ли эти два способа работать параллельно, какой из них основной и что произойдёт, если
внешний платёжный сервис окажется недоступен.

Также вопрос: не проще ли пользователю один раз пополнить баланс на нужную сумму, чем каждый раз
переходить на внешний сервис оплаты?

### Не описан способ возврата либо отмены покупки

Что если юзер не забрал предмет или не успел это сделать? Не отправил заявку в друзья, или, как
говорилось, бота невозможно добавить (бот заблокирован, не хватает места в списке друзей или при
покупке был указан неправильный никнейм). Есть ли определённый промежуток времени, за который юзер
должен забрать предмет — например, 30 минут или 24 часа?

Может быть и проблема с RabbitMQ: если он окажется недоступен в момент оплаты — как сообщение
потом попадёт в очередь?

### Непонятно, что происходит с курсом валют и когда он фиксируется

Не описано чётко, используется ли для расчёта внешний сервис или курс считается локально. Оплата
идёт в BRL, а расчёт — в евро, поэтому непонятно, когда фиксируется курс: раз в день, раз в час,
раз в полчаса, или вообще в момент покупки. И самое главное — кто несёт убытки при колебаниях курса,
мы или пользователь?

### Нет валидации на двойной клик

Будет ли генерироваться уникальный `order_id` при покупке, чтобы предотвратить повторную покупку
одного и того же предмета?

## 2. Граничные сценарии

### Оплата и баланс

| Сценарий | Риск |
| --- | --- |
| Два параллельных клика по кнопке покупки | Двойное списание баланса за один пет |
| Вебхук от платёжной системы пришёл дважды | Двойное начисление баланса или двойная отправка в очередь |
| Вебхук задержался на длительное время | Юзер не понимает, почему заказ всё ещё в обработке, хотя должен быть готов к выдаче |
| Вебхук пришёл с поддельными данными (идентификаторы, подпись и т.д.) | Зачисление баланса или покупка без реальной оплаты |
| Курс валют изменился в момент оплаты | Юзеру приходится платить либо больше, либо меньше ожидаемого |
| Юзер закрыл страницу после редиректа на оплату | Деньги списаны, заказ не создан |

### RabbitMQ и очередь

| Сценарий | Риск |
| --- | --- |
| Сообщение обработано дважды | Бот попытается передать пета дважды |
| Сообщение потеряно в очереди | Потеря пета без возврата средств / отмены заказа |
| RabbitMQ недоступен в момент покупки | Сообщение не попадает в очередь, а деньги уже списаны |
| Бот завис, очередь не движется | У всех юзеров статус «В обработке», очередь растёт |

### Roblox и бот

| Сценарий | Риск |
| --- | --- |
| Таймаут — бот готов к трейду, а юзер не заходит в игру | Бот не может найти юзера, и пет не передаётся |
| Юзер не отправил заявку в друзья | Бот не может передать предмет юзеру |
| Юзер вышел с сервера до принятия трейда | Трейд отменён, но статус на сайте не обновился |
| Сервер Roblox упал во время трейда | Трейд отменён, и непонятно, что станет со статусом |
| Computer Vision не распознал передачу | Пет передан, но статус не обновился на Success |
| Аккаунт бота заблокирован, удалён или не работает | Заказы под этим ботом блокируются, очередь останавливается |
| Бот не смог принять заявку в друзья от юзера | Бот не может передать предмет юзеру |

### WebSocket и фронт

| Сценарий | Риск |
| --- | --- |
| Соединение WebSocket разорвалось / пропало | Статус не обновляется |
| Статус Success пришёл по WebSocket, но Computer Vision не подтвердил передачу | Преждевременный Success |
| Юзер обновил страницу во время трейда | Статус должен подтягиваться из БД, а не только через WebSocket |

## 3. Пострелизный мониторинг

- После релиза необходимо следить за чатом поддержки на предмет падений функционала: петы не
  передаются, оплата не проходит, кто-то нашёл лазейку и подделывает транзакции, обнаружил
  уязвимость в системе с балансом и т.д.
- Если есть возможность смотреть логи — отслеживать процент неуспешных заказов и ошибки API
  (4xx/5xx), разбираться, связано ли это с нехваткой баланса у пользователей или со сбоем
  платёжного провайдера/метода. Следить за событиями вроде `order_created`, `order_success` —
  процент успешных должен стремиться к 100%, поскольку речь о финансах.
- Проверять, не забилась ли очередь и продолжают ли заказы обрабатываться дальше.
- Прогонять небольшой смоук-тест по новому и старому функционалу, не затрагивая продовые данные и
  финансы — с использованием DevTools для проверки API и т.д.
- Проверять консоль на JS-ошибки, если что-то падает на фронте.

# Блок 2. Автоматизация (код)

Код автотестов находится в этом репозитории — API-тесты в [src/tests/api](src/tests/api), UI-тест
(каркас) в [src/tests/ui](src/tests/ui).

## Как запустить проект локально

### Требования

- Node.js версии 22.x ([nodejs.org](https://nodejs.org))
- Установленный Google Chrome — конфиг запускает браузер через `channel: 'chrome'`
  ([playwright.config.ts](playwright.config.ts)), то есть используется реальный системный браузер,
  а не сборка Chromium из комплекта Playwright

### Установка

```bash
git clone <ссылка-на-репозиторий>
cd test-automation-playwright
npm install
```

### Переменные окружения

Перед запуском создайте в корне проекта файл `.env.dev` (он не попадает в git — см.
[.gitignore](.gitignore)) со следующими переменными:

```
API_BASE_URL=https://reqres.in/api/
REQRES_API_KEY=<ваш ключ>
```

Бесплатный API-ключ для [reqres.in](https://reqres.in) можно получить на
[app.reqres.in/api-keys](https://app.reqres.in/api-keys). Без ключа тесты, проверяющие позитивный
сценарий и идемпотентность, не смогут авторизоваться — а вот негативные сценарии (проверка
401/403) как раз и рассчитаны на запуск без валидного ключа или вовсе без него.

### Запуск тестов

```bash
npm test            # все тесты в headless-режиме
npm run test:headed # запуск с видимым браузером (полезно для UI-тестов)
npm run test:ui     # Playwright UI Mode — пошаговая отладка тестов
```

По умолчанию используется окружение `dev` (`.env.dev`). Чтобы переключиться на другое окружение,
передайте переменную `TEST_ENV` перед командой, например:

```bash
TEST_ENV=stage npm test
```

(для этого предварительно понадобится создать соответствующий файл `.env.stage`).

### Просмотр отчёта

После прогона Playwright формирует HTML-отчёт. Открыть его можно командой:

```bash
npx playwright show-report
```
